## 2. 踩坑与校准

### 2.1 最大的事实错误：以为现有 72ch 行宽

初始假设来自 `docs/BLUEPRINT.md:962-963` 和 `tokens.css:180` 的 `--qm-content-max: 72ch`。逐行检索后发现：

- `--qm-content-max` 只在 `tokens.css:180` 定义，`apps/`、`packages/` 没有消费点。
- 编辑器只有 `.cm-content` / `.cm-line` 的 20px writing inset（`theme.ts:35-45`），没有最大宽度。
- 因此当前编辑器是“全宽 + 换行”，不是 72ch。

影响：

- 方案不得声称“保持 72ch”。
- WCAG 1.4.8 的行长要求当前没有被保证；这是独立缺口（Q-004）。
- 任何“字体调整会保持行长”的说法都是错误的；字号变化会改变每行字符数。

教训：设计文档里的值不等于运行时代码的值；必须用 `rg` + 实际选择器确认。

### 2.2 `UiSnapshot` 的相等性是硬编码的

`uiStore.ts:252-259` 只比较 `theme/resolvedTheme/language`。如果新增 `typography` 但忘记加入比较：

- `setTypography` 会写 localStorage；
- `replaceSnapshot` 会认为“没变化”而 early-return；
- React 订阅者/`useEditorTypography` 不会更新；
- 表现为“设置窗口改了，编辑器没反应”，且没有报错。

这是本次最容易被低估的静默 bug。方案在 T-005 明确要求加入 `editorTypographyEquals`，并在 `uiStore.test.ts` 增加“变化会通知”的用例。

### 2.3 `watchUiStorage` 漏 key 是静默的

`uiStorageSync.ts:11-19` 只处理 theme/language/null；其他 key 被静默忽略。

- 写入窗口自身会立即更新（store 订阅者）。
- 其他窗口不会收到通知，直到重载或另一个已监听 key 变化。
- 没有日志/警告。

方案在 T-005 要求加入新 key，并把 `uiStorageSync.test.ts` 的期望从 3 次改为 4 次。

### 2.4 `Object.freeze` 是浅冻结

`uiStore.ts:260` 的 `Object.freeze(next)` 只冻结快照顶层。如果 `typography` 是嵌套对象且未冻结：

- 任何持有快照的代码都可以改 `snapshot.typography.fontSize`；
- `useSyncExternalStore` 的身份/不可变契约被破坏；
- 可能出现“值变了但没通知”。

方案让 `normalizeEditorTypography` 返回 `Object.freeze` 的对象，保证嵌套不可变。

### 2.5 `ThemeStorage` 没有 `removeItem`

`uiStore.ts:26-29` 只有 `getItem/setItem`。如果“恢复默认”要删除 key：

- 需要扩展接口；
- 需要更新所有 fake storage（`uiStore.test.ts:13-40`）；
- 需要处理删除失败。

方案选择“恢复默认 = 写入默认 JSON”，不删除 key。语义清晰、实现最小；代价是 key 始终存在（但值等于默认，无副作用）。

### 2.6 `EditorSession` 是 CRITICAL，不是“随便加个方法”

GitNexus：89 impacted / 43 direct / 23 processes / 8 modules。新增一个字段/方法本身是局部的，但它处在调用图中心。

必须：

- 只加最小 API（option/field/apply/get），不改 snapshot 形状；
- 跑全量 Vitest；
- 跑关键 E2E（theme、editor-binding、reload、minimap）；
- 提交前 `detect_changes`。

不能：

- 用 `EditorSession` 的重建路径实现字体切换；
- 改 `EditorSessionSnapshot` 的字段（会波及状态栏/测试）；
- 在 `replacePayload` 里忘记传 typography。

### 2.7 `themeExtension` 是 HIGH，不要扩它

`themeExtension` 同时承载颜色与 `syntaxHighlighting`（`theme.ts:334-343`），GitNexus HIGH（22 impacted / 4 processes）。

如果把 typography 塞进 `themeExtension`：

- 每次改字号都会重配高亮样式；
- `theme.test.ts`/`editor-binding.test.tsx` 的契约被扩大；
- 风险从 LOW/MEDIUM 升级为 HIGH。

方案新增独立 `typographyExtension`，是正确的边界。

### 2.8 CM6 不会因为纯 CSS 变量自动测量

`@codemirror/view@6.43.15`：

- theme facet 变化 → `mustMeasureContent = true` → `requestMeasure()`（`8094-8097`）。
- ResizeObserver 只观察 `scrollDOM`（`7234-7240`）。
- `measure()` 只在 `measureContent` 为真时重读 `lineHeight/charWidth`（`6386-6390,6447-6452`）。

因此：

- 纯 CSS 变量 + 手动 `requestMeasure()` 在“只换字体族、行盒高度不变”时可能不刷新 `charWidth`。
- 必须用 `EditorView.theme` 让 theme facet 变化。

### 2.9 minimap 已经处理 reconfigure，但 glyph 不连续缩放

- `minimap.ts:489-503` 观察 `view.dom/scrollDOM/contentDOM`。
- `minimap.ts:543-548` 在 `transaction.reconfigured` 时 `scheduleRebuild(0)`。
- `minimapLineHeight/CharWidth` 来自 `view.defaultLineHeight/defaultCharacterWidth`，在 `updateScale()` 读取。
- glyph mask 固定 `bold 11px`，按 `fontFamily` 缓存；字号变化只改变行距/字符宽阶梯。
- **例外：** `MinimapController.update` 在 `view.composing` 时直接 return（`minimap.ts:530-532`）；因此 `applyTypography` 在 composition 期间延迟 dispatch 到 `compositionend`（与 placeholder/uiCopy 一致）。

结论：不需要改 minimap；但不要承诺“minimap 字形随字号连续缩放”。

### 2.10 嵌套代码块的排版是两套（但不能简单删外层）

`nestedCodeTheme`（`code-blocks.ts:177-204`）与 `livePreviewTheme`（`live-preview/theme.ts:1302-1324`）几乎逐条重复：

- `fontSize: inherit`
- `fontFamily: mono`
- `lineHeight: 1.75`
- `.cm-content` padding/caretColor
- `.cm-line` padding
- `.cm-gutters` display none
- `.cm-activeLine` background transparent

**R2 评审发现这是 BLOCKER：不能删除外层六块。** 嵌套编辑器声明顺序是 `qingmoEditorTheme` 在前、`nestedCodeTheme` 在后（`code-blocks.ts:669-670`）；CM6 先声明的扩展优先级更高、style module 反序挂载（`@codemirror/view/dist/index.js:8380-8383`），所以 `nestedCodeTheme` 的同 specificity 规则会输给 `qingmoEditorTheme`。R2 探针复现：删除外层六块后，serif/sans 模式下嵌套代码的 `.cm-scroller` 变成 serif/sans、`.cm-content` padding 回到 28px/20px、`.cm-line` padding 回到 0/20px、`.cm-editor` height 变 100%。

方案改为：**保留外层六块**，只把两处 `1.75` 改为 `EDITOR_LINE_HEIGHT` 常量。这样既消除行高字面量双源，又不改变样式所有权。

### 2.11 Settings 窗口固定 1120×720

- `settings.rs:7-9,60-63`：不可缩放。
- 内容宽约 680px（`1120 - 2px 边框 - 326px rail - 112px padding`）；有滚动条时约 670px。`.settings-row` 两列 + 30px gap；控件 300px，copy 列约 350px。
- 新增内容只能纵向滚动（`settings.css:366-378`）。

不能：

- 依赖拉大窗口；
- 把三个 248px 的 `.settings-select` 并排；
- 直接复用 `LanguageSelect`（它会带来 250 行组件 + 180 行 CSS）。

### 2.12 i18n / text-scan 的硬约束

- `i18n.test.ts:71-97`：中英 key 集合、插值必须一致。
- `text-scan.test.ts:49-64`：`.tsx` 不得出现汉字，中文只能放 `zh-CN.ts`。
- `text-scan.test.ts:66-78`：禁止 `i18nextLng` 作为第二个语言持久键。
- 没有编译期 key 校验；只能靠运行时测试。

新增文案必须同时改 `en.ts` 与 `zh-CN.ts`；否则 `pnpm test` 会红。

### 2.13 `useLayoutEffect` 的顺序依赖

- `EditorHost` 用 passive `useEffect` 创建 view（`EditorHost.tsx:39-51`）。
- `WorkspaceLayout` 的 `useLayoutEffect` 先于子组件 passive effect 运行。
- 因此可以在 view 创建前把 typography 写入 state。

风险：

- 如果未来把 `EditorHost` 改成 `useLayoutEffect`，顺序会变化；
- StrictMode 的 mount→cleanup→mount 需要 E2E 验证；
- 这是 React 语义推断，不是浏览器实测。

### 2.14 localStorage 写失败的语义

`persist` 失败返回 false（`uiStore.ts:267-278`）。方案选择：

- 当前会话仍应用新值；
- `typographyPersistenceDegraded = true`；Settings 首次失败弹一次 `toast.typographyPersistenceFailed`；
- 此后收到 **theme/language** 的 storage 事件时，`syncFromStorage(changedKey)` 保留内存中的 typography，不回滚；只有 typography key 或 `localStorage.clear()` 才采用外部值并清除降级；
- 重启回到旧值。

这比“只写 localStorage、失败静默”更可靠；与 `languagePersistenceDegraded` 的语义对齐。

## 4. 明确不要做

1. 不要用 `EditorView.setState` 或重建 `EditorState` 实现字体切换。
2. 不要把 typography 塞进 `themeExtension`。
