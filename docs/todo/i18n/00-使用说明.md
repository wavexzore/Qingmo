# LLM 持续实施模板 — 使用说明

> 适用位置：`docs/todo/<功能名称>/`  
> 核心用途：让 LLM 能够在多轮会话中稳定读取状态、选择下一步、实施、验证、记录证据并恢复执行。  
> 设计原则：**任务可解析、状态可恢复、完成有证据、失败可回滚、范围可约束**。

---

## 1. 这个模板解决什么问题

普通实施方案适合人类阅读，但不一定适合 LLM 长周期执行。LLM 持续实施需要额外满足：

| 需求 | 模板约束 |
|---|---|
| 知道当前做到哪一步 | `README.md` 的 `LLM-STATE` 块记录当前任务、状态、下一步 |
| 能自动选择下一项任务 | `01-实施计划.md` 使用稳定 `T-###` 任务队列和依赖关系 |
| 不重复做已完成工作 | 每个任务有 `Status`、`Evidence`、`CompletedAt` |
| 不随意扩大范围 | 每个任务必须声明 `Files`、`Allowed Scope`、`Out of Scope` |
| 完成后能证明 | `02-实施状态与验证.md` 使用 `C-###` 命令记录和验收覆盖 |
| 失败后能恢复 | 每次失败记录 blocker、尝试、下一恢复动作 |
| 调研结论可复用 | `01-实施计划.md` 固化官方文档、GitHub 开源实现、版本约束和采用/拒绝理由 |
| 调用链分析可追踪 | `01-实施计划.md` 固化 subagent/GitNexus 调用链、数据流、配置流、错误流和影响面证据 |
| 每个任务实时校准 | `T-###` 执行前必须重新确认当前代码、候选文件、调用链和计划是否仍匹配 |
| 人类仍能审查 | README 保留摘要、风险、验收和交付物视图 |

---

## 2. 推荐目录结构

```text
docs/todo/<功能名称>/
├── 00-使用说明.md          # 模板说明；实际功能目录可保留或删除
├── README.md               # LLM 执行控制台：状态、范围、下一步、验收
├── 01-实施计划.md          # LLM 任务队列：T-ID、依赖、步骤、验证、状态
├── 02-实施状态与验证.md    # 执行日志与验证证据：C-ID、结果、覆盖、VERDICT
└── 03-复盘与交接.md        # 决策、踩坑、回滚、维护和交接
```

> LLM 每次恢复执行时必须优先读取：`README.md` → `01-实施计划.md` → `02-实施状态与验证.md`。

---

## 3. LLM 执行协议

### 3.0 实施方案生成前（中大型任务必做）

当任务涉及中大型功能、架构调整、跨模块修改、外部 SDK/API/框架、数据库/部署/安全/性能时，LLM 在生成 `01-实施计划.md` 前必须完成：

1. **官方文档调研**：优先读取框架、SDK、数据库、中间件、部署工具的官方文档或一手资料。
2. **GitHub 开源实现调研**：参考 2~5 个相关高质量开源项目，记录可借鉴点和不采用原因；不得直接照抄代码。
3. **subagent + GitNexus / 代码索引深度分析**：分析入口、核心调用链、数据流、配置流、错误处理流、测试覆盖和影响面。
4. **候选目标验证**：涉及多个候选文件/符号时，必须列出候选对比，避免锚定第一个搜索结果。
5. **证据落盘**：调研和调用链结论必须写入 `01-实施计划.md`；执行过程和命令证据写入 `02-实施状态与验证.md`。

如某项不适用，必须在 `01-实施计划.md` 写明“不适用原因”，不能留空。

### 3.1 每轮开始

LLM 开始实施前必须：

1. 读取 `README.md` 的 `LLM-STATE`。
2. 读取 `01-实施计划.md` 的任务队列。
3. 读取 `02-实施状态与验证.md` 的最新执行日志。
4. 选择第一个满足以下条件的任务：
   - `Status = todo` 或 `Status = blocked` 且有恢复动作；
   - 所有 `DependsOn` 都是 `done` 或 `skipped`；
   - 当前任务文件范围与用户授权范围一致；
   - 执行前实时校准通过：相关文件仍存在、调用链仍匹配、计划未落后于代码。
5. 如实时校准发现计划已过期，先更新 `01-实施计划.md §13` 和 `02-实施状态与验证.md §8`，再实施。
6. 将 `README.md` 的 `current_task` 更新为该任务。

### 3.2 每个任务实施中

每个 `T-###` 任务必须遵循：

```text
读取任务 -> 确认依赖 -> 实时校准代码/调用链 -> 限定文件范围 -> 实施最小切片 -> 运行该任务验证 -> 写执行日志 -> 更新任务状态
```

禁止：

- 没有证据就把任务标记为 `done`。
- 跳过依赖任务直接实施下游任务。
- 修改 `Files` 之外的文件且不记录变更原因。
- 只写“已完成”，不写文件、命令、测试或日志证据。
- 遇到失败后反复尝试同一种方法而不记录 blocker。

### 3.3 每轮结束

LLM 停止前必须更新：

1. `README.md`：`LLM-STATE`、当前状态、下一步。
2. `01-实施计划.md`：当前任务状态、证据、完成时间。
3. `02-实施状态与验证.md`：命令结果、失败原因、验收覆盖。

## 4. 状态枚举

### 4.1 功能状态

只使用以下值：

```text
todo | in_progress | blocked | partial | done | rolled_back | cancelled
```

### 4.2 任务状态

只使用以下值：

```text
todo | in_progress | blocked | done | skipped
```

### 4.3 验证状态

只使用以下值：

```text
not_run | pass | fail | partial | skipped
```

### 4.4 最终 VERDICT

`02-实施状态与验证.md` 必须以以下之一结束：

```text
VERDICT: PASS
VERDICT: FAIL
VERDICT: PARTIAL
```

## 5. ID 规范

| 类型 | 格式 | 用途 |
|---|---|---|
| 需求 | `R-001` | 功能需求或验收需求 |
| 决策 | `D-001` | 关键技术/产品决策 |
| 修改点 | `MP-001` | 设计方案中的修复修改点（`04-设计方案.md` §4） |
| 任务 | `T-001` | LLM 可执行任务 |
| 命令 | `C-001` | 验证命令或检查 |
| 风险 | `RK-001` | 风险与回滚项 |
| 问题 | `B-001` | blocker 或失败项 |
| 后续 | `NEXT-001` | 非当前范围后续事项 |

## 6. 证据规范

“完成”必须绑定至少一种证据：

| 证据类型 | 示例 |
|---|---|
| 代码路径 | `src/foo/bar.ts:handleRequest` |
| 测试文件 | `tests/foo.test.ts:shouldHandleError` |
| 命令 | `npm test -- tests/foo.test.ts` |
| 日志 | `.jssdd/specs/<spec>/runtime/events.jsonl` |
| 接口 | `POST /api/foo` |
| 配置 | `FEATURE_FOO_ENABLED=false` |
| GitNexus | `impact: LOW, affected_processes: ...` |
| 官方文档 | `GoFrame official docs: MonoRepo app entry is app/<name>/main.go` |
| GitHub 参考 | `repo owner/name: borrowed directory pattern, rejected direct code reuse due to license/complexity` |
| subagent 分析 | `explore/debugger/verifier: call chain entry -> service -> repository` |

不要写：

```text
Status: done
Evidence: 已完成
```

应该写：

```text
Status: done
Evidence: `src/foo/bar.ts:handleRequest` 新增异常分支；`npm test -- tests/foo.test.ts` 通过，C-003。
```

## 7. 与项目内置 SDD 方案的关系

| 项 | 作用 |
|---|---|
| 项目内置 `requirements/design/tasks/verification` | 流程契约，适合插件/validator/agent 自动推进 |
| `docs/todo/<功能名>` | LLM 执行控制台，适合跨会话持续实施和交付记录 |

推荐关系：

1. 若已有 `.jssdd/specs/<spec>/tasks.md`，将任务同步到 `01-实施计划.md`。
2. LLM 实施时以 `docs/todo/<功能名>/README.md` 的 `LLM-STATE` 为恢复入口。
3. 完成后把最终证据同步回项目内置 `implementation-log` / `verification-report`，如果该流程正在使用。

## 8. 实施前检查清单

- [ ] `README.md` 是否包含完整 `LLM-STATE`？
- [ ] 是否明确 `allowed_scope` 和 `forbidden_scope`？
- [ ] 是否有 `R-###` 需求/验收项？
- [ ] 是否有 `T-###` 任务队列？
- [ ] 每个任务是否有 `DependsOn`、`Files`、`Steps`、`Verification`？
- [ ] 是否有回滚方案？
- [ ] 是否识别安全、权限、数据兼容、配置默认值风险？
- [ ] 是否完成官方文档或一手资料调研？如不适用，是否写明原因？
- [ ] 是否完成 GitHub 开源实现对比？如不适用，是否写明原因？
- [ ] 如项目启用 GitNexus，是否完成影响分析？
- [ ] 是否完成 subagent/GitNexus 深度调用链、数据流、配置流、错误流分析？
- [ ] 每个 `T-###` 是否包含 Pre-Implementation Check？

---

## 9. 实施后检查清单

- [ ] 所有必须任务是否为 `done` 或有明确 `skipped` 理由？
- [ ] 每个 `done` 任务是否有证据？
- [ ] 是否记录验证命令 `C-###`？
- [ ] 是否覆盖正常、异常、边界、回归场景？
- [ ] `VERDICT` 是否为 `PASS` 或明确 `PARTIAL/FAIL` 原因？
- [ ] `README.md` 的 `next_action` 是否准确？
- [ ] 是否记录剩余风险和回滚方式？

---

## 10. 模板裁剪建议

如果任务较小，至少保留：

- `README.md`
- `01-实施计划.md`
- `02-实施状态与验证.md`

如果任务只做复盘，可以保留：

- `README.md`
- `02-实施状态与验证.md`
- `03-复盘与交接.md`
