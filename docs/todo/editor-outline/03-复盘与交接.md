## 1. 这版方案与实现解决了什么

以下 8 点均已落地，实施证据见 `02-实施状态与验证.md` §3~§9。

1. 明确了“大纲”是**文档标题结构导航**，不是文件树、不是代码符号大纲、不是 `[TOC]` 占位符的替代品。
2. 找到了唯一正确的标题模型位置：`editor-core` 的 `headingOutline` StateField，放在 `createEditorState` 基座，Source/Live Preview 都存在。
3. 解决了三套标题扫描的分叉风险：TOC、标题锚点、侧栏全部消费同一个字段；minimap 的行扫描保持独立（它是 presentation-only）。
4. 解决了 CM6 初始语法树只有 3000 units 的问题：字段监听 `docChanged || syntaxTree !==`，`outlineParseDriver` 用 8ms 空闲切片推进到 200k。
5. 解决了 React 第二份文档副本的问题：`EditorSession` 新增独立 outline 订阅，标题文本不进入 `EditorSessionSnapshot`。
6. 解决了 StrictMode 下 attach→detach→attach 重复 update listener 的风险：代际 id 守卫。
7. 明确了默认隐藏、零持久化、零新 IPC 的安全默认值；回滚只需移除面板/命令。
8. 给出了可执行的测试矩阵：字段/排除/限额、Session/StrictMode、面板/活动项、E2E/性能/可访问性。

## 3. 踩坑与纠正记录（设计阶段）

### 3.1 初始语法树不是全文

CM6 `LanguageState.init` 只解析 `min(3000, doc.length)`。如果 `headingOutline.create` 只遍历 `syntaxTree(state)`，大纲会长期只有前几个标题，直到用户滚动或文档变化。

**纠正**：

- 字段监听 `syntaxTree(tr.state) !== syntaxTree(tr.startState)`，树推进时重建。
- 新增 `outlineParseDriver`，在 ViewPlugin 中按 `OUTLINE_PARSE_CHUNK_UNITS` 分块推进（每块目标为“当前树 + 50k”），用 `forceParsing` 返回值判断是否推进下一块；同一 target 最多重试 16 次（`false` 不代表 context 未推进），仍失败就暂停并保留 partial，滚动/编辑触发 doc/viewport 变化后恢复。Chromium 用 8ms 空闲切片，且同一个回调内可连续推进多个块；WKWebView 用 64ms/4ms fallback。
- partial 状态显式展示，不假装完整。

**否决**：Zettlr 在 `tocField` 内 `ensureSyntaxTree(state, doc.length, 1000)`。它能一次拿全树，但把解析放在 state 更新路径上，最坏阻塞 1s；对输入延迟不可接受。

### 3.2 三套标题扫描不能变成四套

现有 `toc.ts:scanDocument`、`heading-anchors.ts:readHeadingAnchors` 各扫一遍标题；minimap 的行扫描是第三套（但只用于缩略图）。如果侧栏再写一个 `doc.toString()` + 正则，会出现第四套，且与 Lezer 语义分叉。

**纠正**：

- `headingOutline` 成为唯一标题语义。
- TOC 只扫 `[TOC]` 占位符；锚点只做 slug/去重。
- minimap 保持独立，明确它不是大纲数据源。
- 用 `rg "isHeading\\("` 做验收：`scanPlaceholders`/`readHeadingAnchors` 不再调用；`readHtmlAnchors` 的显式锚点扫描与 `details.ts` 的 details 渲染保留。

### 3.3 `plainInlineText` 与 `details.ts` 的传递循环依赖

`outline.ts` 需要 `plainInlineText` 生成 `plainText`；`heading-anchors.ts` 又需要 `readHeadingOutline`。如果直接互相 import，会形成：

```text
outline.ts -> heading-anchors.ts -> outline.ts
```

更隐蔽的是 details：

```text
outline.ts -> details.ts -> specs.ts -> heading-anchors.ts -> outline.ts
```

`details.ts` 又依赖 `specs.ts`/DOM/i18n，不能作为字段的轻量依赖。

**纠正**：

- 把 `plainInlineText` 移到 `heading-text.ts`；`heading-anchors.ts` re-export，保持现有测试/公共导入不变。
- 新增 `details-range.ts`：只做 `<details>` 标签配对和顶层闭合范围，不依赖 `specs.ts`/DOM/i18n；`outline.ts` 只依赖它。
- `details.ts` 复用 `details-range.ts` 的 `scanDetailsTags`，签名/渲染不变。
- 这是 T-002 的 Pre-Implementation Check 必查项。

### 3.4 `tocPreview` 的 impact UNKNOWN 不能当“未使用”

GitNexus 对 `tocPreview` 返回 `impactedCount: 0 / risk: UNKNOWN`，但 `plugin.ts:225` 把它放进 `livePreview()` 扩展数组，`corpus.test.ts:85` 用 `state.field(tocPreview)`。这是“值引用”而非函数调用，图索引无法解析。

**纠正**：

- 保留 `tocPreview`，只改内部扫描。
- 任何“删除 tocPreview”的方案必须先文本检索并跑 corpus 测试。

### 3.5 StrictMode 会重复 append update listener

`EditorSession.attachUpdateListener` 每次 attach 都 `appendConfig` 一个新 listener；StrictMode 会 mount→cleanup→mount。实际有两种路径：React 创建**新 view**时，旧 listener 由 `this.view !== view` no-op；同一 view 的 detach→attach 或 `replacePayload` 重挂时，`this.view` 仍相同，必须靠代际 id。

**纠正**：

- `attachmentId` 代际；listener 闭包捕获 id，`this.attachmentId !== id` 时 no-op。
- `detach`/`dispose` 递增 id。
- UT-017 覆盖新 view 路径，UT-018 覆盖同一 view 重挂 + `replacePayload`。

### 3.6 菜单多处 + 生成绑定

真实 Tauri 菜单需要：

1. Rust `contract.rs` 的 `MENU_ACTIONS`；
2. TS `commands.ts` 的 `MENU_ACTIONS`；
3. TS `MENU_ACTION_NAMES`；
4. `NativeShellLabels` 字段 + 生成绑定；
5. Rust 菜单布局；
6. zh/en 文案。

只改前两处时，FakePlatform/E2E 仍会通过，但真实 Tauri 会忽略动作。**纠正**：同一提交闭环，`commands_contract.rs` 断言 `MENU_ACTIONS.len() == 12`，`native.test.ts` 断言字段与 menu JSON key 完全相等。

### 3.7 默认打开会破坏现有 E2E

现有 `e2e/minimap.spec.ts` 在 600/800/1200px 断言布局；如果大纲默认打开，640px 编辑器会被 240px 面板挤压，导致 margins/宽度断言失败。**纠正**：默认隐藏；打开后才让位；<900px CSS 隐藏（240 面板 + 640 编辑器 + 边距）。

### 3.8 `details.ts` 不要为了传树而改签名

`readDetailsBlocks` 的 GitNexus impact 是 CRITICAL（42 impacted）。本方案只需要复用它的标签配对能力，不需要把 ensured tree 传进去。新增 `details-range.ts` 的 `readDetailsRanges` 与 preview 的 block-widget cap 对齐：`doc.length > PREVIEW_FULL_MAX_UNITS` 返回空范围（details widget 不渲染，标题按可见源码处理），≤200k 时排除闭合 details；`details.ts` 只把正则循环替换为 `scanDetailsTags`，签名/嵌套/渲染输出不变。

解析未完成时状态是 partial；等 `syntaxTree(state)` 发布后再 complete，避免“标题看到全文、details 只看到前缀”的不一致。

## 8. 已知限制

1. 只显示 Document 顶层标题；`<details>` 内标题不显示（与现有 TOC 一致）。`readHeadingAnchors` 直接调用在 ≤200k 时也会排除闭合 details，这是单一模型的有意收敛；`specs` 的 `blocked` 调用输出保持一致。
2. 超过 200k units 只显示前缀；字段安全上限 5000 条，面板只显示前 500 条；第 501 条以后仍可生成锚点；但超过 200k 的标题不在字段内，锚点只覆盖前缀。>200k 时 details widget 不渲染，`readDetailsRanges` 返回空，其中标题按可见源码进入大纲（与 preview 一致）。
3. 活动项跟随光标，不跟随视口滚动（与 Typora 不同）。
4. 侧栏纯文本，不显示加粗/链接样式。
5. 不持久化开关；新窗口默认关闭。
6. 不提供大纲内搜索/过滤/折叠/拖拽/编号。
7. 不修复标题 slug 冲突。
8. 原生菜单不显示 checked 状态。

这些限制均在 README §2.2 与 04 §2.4 中有对应 NEXT/Q。

### 10.2 与设计的偏差

1. **解析分块 10k → 50k**：10k 分块下 200k 打开 p95 为 387ms；改为 50k 且允许同一 8ms 回调连续推进多块后，p95 180.8ms。单块仍远小于总预算，输入长任务保持 0。
2. **`plainInlineText` 快速路径**：纯文本标题不再跑 6 个正则，改为一次字符类检测；5000 标题路径 p95 从 20ms+ 降到 3.04ms。
3. **`details.some` 短路**：无 details 时不做空数组遍历，去掉每个顶层块的固定开销。
4. **bench worker 内存参数**：`vitest.bench.config.ts` 增加 `--max-semi-space-size=256 --max-old-space-size=4096`，避免测量循环自身的 scavenge 进入 p95；浏览器 GC 由 E2E-016 的长任务单独覆盖。
5. **E2E 落点断言修正**：CM6 的 `EditorView.scrollIntoView(pos, { y: "start", yMargin: 10 })` 对齐的是行盒，标题内联盒还有 3px 行内边距。E2E-003 改为测标题内联盒顶部，得到真实的 10±2px。
6. **跳转动画（交付后增强）**：`revealPosition` 改为 selection 立即落点 + `scrollTop` 120–280ms `easeInOutCubic`，再用 `coordsAtPos` 做 120ms 收尾校正；reduced motion 瞬时。E2E-003 采样到多个中间 `scrollTop`，证明不是硬切。

### 10.3 经验

- CM6 初始语法树只有 3000 units，任何“打开即完整”的假设都会失败；字段必须监听树变化，且需要独立的推进器。
- 纯函数 bench 的 p95 很容易被 GC 主导；不隔离 GC 就会把“测量噪声”误判成“算法退化”。
- 共享字段的收益是真实的：TOC 与锚点改造后，`scanPlaceholders` 只剩占位符扫描，标题语义只有一处。
- 回滚演练应作为交付物的一部分：它能证明面板与命令是独立可移除的，而不是散落在布局与路由里。
