## 1. 最终结论

本方案把 P0/P1 收尾拆成三条共享底座的主线：

1. **文档身份**：新增持久 `DocumentId`，把历史、视图状态、窗口恢复从 path 键迁移到文档身份；`FileIdentity` 只用于 rename 配对和 TOCTOU 复核；文件锁保持 path-hash。
2. **边界与所有权**：统一 16 MiB 文档上限；所有文档命令校验窗口归属；Save As 释放 current+previous token；watcher 定向投递；rekey 后通知窗口更新 path/title/asset scope。
3. **可达性**：虚拟树 10k 首帧 DOM 有界、离屏焦点可达、ARIA 完整；回收站同卷/跨卷恢复与删除对称。

方案已完成研究、GitNexus/subagent 调用链分析、源码逐行校准、基线测试和 R1~R14 评审；T-001~T-015 已全部实施并通过自动化验证。Q-001 ~ Q-008 已于 2026-11-09 全部批准（A/A/B/A/A/A/A/B）；已提交并复跑 `pnpm ci:local` 全绿；剩余外部环境/人工验收项为 B-002/B-003，B-001/B-004/B-005 已关闭。

核心判断：

- 原子保存会更换 inode，因此“用 inode 当文档 ID”不可行；稳定 ID 必须持久化映射。这是本方案与“纯 file-id 方案”的根本区别。
- **live record 的 `document_id` 是权威**；History/View 直接接收 ID，不在使用时重新 `observe(path)`；rekey 只 `adopt`，绝不重新分配 ID。
- 文件锁继续使用 path-hash：它跨版本、跨 identity 故障稳定；改 DocumentId 会导致新旧版本不互斥、disabled 时失效。
- 不新增第二套写盘/读取/watcher/路径解析；所有改动落在现有组件上。
- 搜索索引仍是可重建缓存，不引入持久身份表；rename 只做事件迁移。
- 唯一新增持久数据文件是 `identity/documents.json`，已经 Q-002 批准；不新增 SQL 表、不新增用户配置项。
- `disabled()` 完全使用 legacy 键（history path-hash、view path、lock path-hash），不生成伪 ID；Windows/回滚安全。

## 6. 回滚方案

### 6.1 按变更回滚

| 变更 | 回滚步骤 | 数据影响 | 验证 |
|---|---|---|---|
| 16 MiB 统一上限 | **保留 16 MiB 读取**，仅阻断 >10 MiB 增长；或发布 hotfix | 已保存 10–16 MiB 文件仍可打开 | C-003 + 回滚打开 10–16 MiB 测试 |

| view-state v2 | 恢复 `view-state.json.v1-backup-*`；dual-read；v2 已保留 legacy path 键 | 新 ID 条目可能丢失，但 legacy 光标仍可读 | C-006 |

### 6.2 回滚顺序

1. 先停用 identity（`disabled()`），确认历史/视图仍通过 legacy 键可读。
2. 再回退 rename 配对/token 校验等行为变更。
3. 回退 verified write/trash，保留 root jail 与 hash 校验。
4. 最后回退 16 MiB 与前端树（16 MiB 必须保留读取）。
5. 数据回滚只在备份副本上执行；默认 dry-run，不删除。

### 6.3 备份点

## 10. 交接结论

- 方案已具备可执行性：任务有依赖/Gates、文件范围、验证命令、失败恢复。
- 最大风险是身份键迁移（RK-002）与 rename 平台差异（RK-003），两者都有回滚路径。
- 最小安全切片是 `T-001 → T-002 → T-004 → T-005 → T-006 → T-008`；推荐先做这一条，再并行 T-003/T-007/T-009/T-011。
- Q-002 已批准，按 A 执行；若未来回退到 B，方案退化为“运行期 rename 配对 + path 键”：能修索引残留、误报 Deleted、目录 rename 和重复实现问题，但无法跨重启保持历史/视图身份；需要在 `01 §14` 记录变更。
- Q-001 已批准统一 16 MiB；若未来回退，必须保留“10 MiB + 1 保存成功”的验收方式（例如只读预览/提示另存），不能让用户“保存成功但打不开”。
